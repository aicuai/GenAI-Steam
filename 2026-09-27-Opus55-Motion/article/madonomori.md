# ついに"リズム感"を手に入れた Opus5.5にモーショングラフィックスを作らせてみた！

## 素材ゼロ、コードだけで15秒の映像と音楽を生成

Anthropic の AI「Claude Opus 5.5」に、モーショングラフィックス（文字や図形を動かして見せる映像）を作らせてみた。できあがったのは15秒・900コマの動画で、映像と音楽がきっちり同期している。画像や音源といった素材ファイルは一切使っておらず、すべて HTML と Python のコードから生成されている。

本稿では、Opus 5.5 が書いたコードを読みながら、映像と音がずれないしくみ、動きや質感の作り方、書き出しの手順を紹介する。作例のソースコードは AICU のサイトで公開しており、手元の PC で同じ動画を書き出せる。

キャプション：4拍目、キックが鳴り始めると同時に「MOVE」の文字が滑り込む

## 依頼はひとことだけ

事前に、別のセッションで Opus 5.5 に「どうやって作ったのか」を説明させた文章を用意していた。「HTML で絵を描き、Python で900コマを撮り、音楽も計算で作り、最後に合体する」という全体の流れと、各工程の考え方を非エンジニア向けにまとめたものだ。この文章を渡したうえで、「Opus5.5でコード生成してみて」と頼んだ。

Opus 5.5 は次の4つのファイルを書いた。

- index.html：映像。指定したコマの絵を描くプログラム
- render.py：書き出し。ブラウザに900コマを描かせ、動画ファイルにまとめる
- make_audio.py：音楽。波形を計算して音声ファイルを作る
- build.sh：上の3つを順に実行し、映像と音声を1本の MP4 にする

さらに Claude の作業環境（チャット内でコードを実行できる機能）で実際に書き出しまで行い、完成した動画を渡してきた。

## すべてを「拍」で書くから、ずれない

この作例の要は、映像の出来事も音も「拍の番号」で書かれている点にある。テンポは128BPM。1拍は0.46875秒で、32拍（8小節）でちょうど15秒になる。60fps で書き出すと900コマだ。

映像のプログラムは、再生時刻を拍に換算した値で場面を切り替える。「4拍目で MOVE が入る」「28拍目で爆発」という具合だ。音楽のプログラムも「4拍目から4つ打ちのキック」「28拍目に大きなキック」と同じ番号で書かれている。映像と音が同じ番号を参照しているので、編集ソフトで波形を見ながら合わせる作業がもともと存在しない。

| 拍 | 映像 | 音 |
|---|---|---|
| 0〜4 | 点が拍ごとに脈打ち、線が伸びる | 拍ごとの電子音 |
| 4〜8 | 「MOVE」が滑り込む | キック開始、和音 |
| 8〜16 | 「SHAPE」「RHYTHM」、図形が変形 | ハット、スネア |
| 16〜20 | グラフエディタ | 和音 |
| 20〜24 | トンネル | 和音 |
| 24〜27.75 | ワイヤーの立方体、グリッチが強まる | 上昇していくノイズ |
| 27.75〜28 | 真っ黒 | 無音（約0.12秒） |
| 28〜32 | 爆発し、粒子が「CLAUDE」に集まる | 大きなキックとクラッシュ |

## 動き・形・質感の作り方

**緩急（イージング）**：文字の動きは、0から1へ進む割合を数式で曲げて作っている。「速く入ってゆっくり止まる」（expo）、「少し行き過ぎて戻る」（back）、「跳ねて止まる」（bounce）の3種類を、MOVE・SHAPE・RHYTHM の文字にそれぞれ割り当てている。16〜20拍目では、この曲線そのものをアニメーション制作ソフトのグラフエディタ風に見せる。

【画像】graph.jpg
キャプション：3種類の緩急の曲線。曲線上の点と、その値で動く四角が拍に合わせて動く

**図形の変形**：丸・四角・三角・星を、どれも「周囲の240個の点」で表している。同じ番号の点どうしを少しずつ動かせば、ある形から別の形へなめらかに変わる。

**奥行き**：トンネルと立方体は 3D ライブラリを使わず、「遠いものほど小さく描く」遠近法の計算を自前で書いている。

**粒子**：最後の「CLAUDE」は、見えない画面に文字を描き、文字の部分の点を約5,000個拾って、そこへ粒子を集めている。

【画像】shape.jpg / tunnel.jpg
キャプション：左は図形の変形の途中、右は自前の遠近法で描いたトンネル

**質感**：映像らしく見せるために、次の処理を重ねている。

- モーションブラー：1コマを、時刻を少しずつずらして10回描き、平均する
- グリッチ：赤と青の成分を左右にずらし、画面を横に切ってずらす
- フィルムの粒子：薄いノイズを毎コマ違う位置に重ねる
- 四隅のタイムコード：背景との差で描く合成方法（difference）を使い、背景色が変わっても読めるようにしている（背景が中間のグレーに近いと読みにくい）

キャプション：爆発の直前。グリッチが最大に近づいていく

## 音楽も計算で作る

音声もサンプル音源を使わず、波形の計算だけで作っている。キックは周波数を一瞬で下げた低い正弦波、ハットやスネアは雑音から不要な帯域を削ったもの、和音は少しずつ音程をずらしたノコギリ波を7本重ねた「スーパーソー」だ。

キックが鳴るたびに他の音を一瞬小さくする「サイドチェイン」で、クラブ音楽らしいうねりも出している。爆発の直前には4分の1拍（約0.12秒）の完全な無音を入れ、映像も同じ区間を真っ黒にした。直後の爆発との落差を大きくするためだ。

## 書き出しのしくみと所要時間

render.py は、Playwright 経由で画面を持たない Chromium（ヘッドレスブラウザ）を起動し、「0コマ目を描いて画像を受け取る」を900回くり返す。受け取った画像は、動画変換ツール ffmpeg にそのまま流し込んで MP4 にする。ブラウザの再生速度に頼らず、コマ番号を指定して描かせるので、重い処理を入れてもコマ落ちしない。

Claude の作業環境（CPU 1コア）では、960×540・ブラー3回の設定で900コマの書き出しに約110秒かかった。1920×1080・ブラー10回の本番設定では、画素数が4倍、描画回数が3倍強になるので、数分から十数分を見込みたい。

## AI が自分で見つけて直したバグ

最初の書き出しでは、最後の「CLAUDE」の文字が赤と青にずれて読めなくなっていた。爆発前に強めていくグリッチの量を計算する式が、予定の区間を過ぎても最大値のまま張り付いていたのが原因だ。

Opus 5.5 は、書き出した動画から十数コマを切り出して一覧画像にし、それを見てこの問題に気づいた。原因の式を特定し、条件を1行足して修正している。映像のように結果が目に見えるものは、コマを並べた一覧を作らせると、人間も AI も見落としに気づきやすい。

## 「リズム感」はどこまで本当か

タイトルの「リズム感」は、Opus 5.5 が音を聴き取れるようになったという意味ではない。make_audio.py は音を読み込むのではなく書き出すプログラムで、映像と音楽は同じ拍番号の表から作られている。同期しているのは、聴いて合わせたからではなく、同じ表から両方を作っているからだ。作業中に Opus 5.5 が確かめたのもコマを並べた画像で、音声は確かめていない。

また、最初に渡した説明文にはすでに「拍」の考え方が含まれていた。そのため、Opus 5.5 が自発的に拍で設計したとまでは言えない。ほかのモデルとの比較もしていない。

コードは Remotion などの動画フレームワークを使っていない（依存は Playwright・NumPy・ffmpeg のみ）。ただし細部には定番の部品がそのまま入っている。イージングは Robert Penner の式で、定数と変数名まで easings.net 掲載のコードと一致する。乱数はパブリックドメインの mulberry32 だ。一方、この作例に固有の行を GitHub のコード検索にかけても、一致するコードは見つからなかった（2026年9月27日時点。検索対象は公開リポジトリの既定ブランチのみ）。1本のテンプレートの流用ではなく、定番の部品を「拍の表」という骨組みに組み立てたもの、というのが実態に近い。

## 手元で試すには

作例のソースコード一式は、AICU の記事ページからダウンロードできる。Python 3 と ffmpeg を用意し、次のコマンドを実行すると本番画質の動画（final.mp4）ができる。

```
pip install playwright numpy
playwright install chromium
./build.sh
```

まず軽い設定で試すなら `./build.sh --scale 0.5 --sub 3` とする。文字は Google Fonts から読み込むため、オフライン環境では代わりのフォントで描かれる。

拍の表と文字、和音の進行を書き換えれば、同じしくみでイベントのオープニングや番組のジングルなど別の映像が作れる。テンポを変えれば尺も自動で変わり、映像と音はそろったままだ。

## 手持ちの曲に合わせるなら

この作例は、手持ちの MP3 には合わせられない。テンポは128BPMに固定されており、曲を読み込む処理がない。既存の曲に合わせるには、曲から拍を見つける処理が要る。

その例が、hakoniwa 氏が MIT ライセンスで公開しているブラウザアプリ「JIZURA（字面）」（https://852wa.github.io/JIZURA/）だ。歌詞から文字PVを組み立てるツールで、曲を読み込むと、音量の立ち上がりの周期を 70〜180BPM の範囲で調べてテンポと拍の位置を決め、カットの切れ目を拍に寄せる。テンポが揺れる曲は、タップ同期や LRC 形式のタイムスタンプで補う。

両者の違いは、音が「出力」か「入力」かにある。この作例は同じ表から音と映像を作るので、しくみ上ずれない。JIZURA は既存の曲に合わせられる代わりに、同期の精度が拍の検出に左右される。演出も、この作例は1本のための専用コードだが、JIZURA は707の部品と24のスタイルを組み合わせて毎回別の構成を作る。

テンポの決め方も対照的だ。この作例は「128BPM」と書いて曲のほうを合わせて作る、いわば決めうちである。JIZURA は、見つかった周期に「125BPM 前後だろう」という仮説で重みをかけて推定する。この重み付けは、Dan Ellis の論文「Beat Tracking by Dynamic Programming」（2007年）と同じ形だ。人がテンポを感じるときの 120BPM 前後への偏りを使って、倍や半分のテンポへの読み違えを防いでいる。

モデルが音を聴いていないということは、拍の時刻さえ分かればどんな曲にも同じ設計が使えるということでもある。BPM が分かっている曲なら BPM と1拍目の位置を書くだけでよい。MIDI があればテンポ情報から拍の時刻を計算できる。MP3 しかなければ、JIZURA や librosa などで拍を推定する。映像側は、時刻を拍番号に直す1行を差し替えれば、場面の分岐をそのまま使えるはずだ（未検証）。

なお、「HTML で描いて動画にする」という枠組みには、Remotion や、HeyGen がエージェント向けに公開している hyperframes などの先行例がある。今回のコードはこれらを使わず、数百行で同じことを書いている。数式も線形ばかりではない。遠近は逆数、拍の脈動やキックの音程は指数関数、バウンスは区分的な放物線、音の飽和は tanh で作られている。
